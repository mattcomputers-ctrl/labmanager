# Decisions

Choices made while building Chroma where the spec said "decide" or left room, grouped by area. The per-area notes in `docs/decisions/` are the source; this file is assembled from them.


## Core and foundation

1. **No framework; small custom core.** `src/Core` is ~1,500 lines: router, PDO wrapper, DB-backed sessions, auth, CSRF, flash, views, validator. It matches the other in-house PHP systems and keeps Composer dependencies to four packages.
2. **Table for project items is `chroma_project_items`** (the spec calls it `project_colors`). It carries a `kind` column (`color`, `trial`, `sample`, `existing_product`) so R&D trials and customer-issue products share the table; the UI still says "Colors" on color-match projects (the label comes from `chroma_project_types.item_label`).
3. **E numbers are unique on (number, version)**, with `version` stored as an empty string rather than NULL so the unique index works in MariaDB. The cross-reference may hold `E6374-10` and `E6374-12` as separate rows; both map to the same base number. Assigning a new E# always creates version `''`.
4. **Sell number normalization** = uppercase prefix + number without leading zeros + uppercase suffix, no hyphens or spaces (`y-1000` → `Y1000`, `UVNG072` → `UVNG72`). The original text is kept in `legacy_text`. Display re-pads to the prefix's `min_digits`.
5. **The `UV` prefix stays `UV`** (not renamed to `UVL`) because it is the code printed on existing products; renaming would change product codes. It is labelled "UV legacy series", tagged "inherited" and sorted to the bottom of the prefix list. Parsing is unambiguous because a prefix is always the leading letters and a suffix the trailing letters. See QUESTIONS.md #3 — easy to rename later from Admin → Prefixes.
6. **Sessions in the database** (`chroma_sessions`) so an admin can see who is signed in and sessions survive PHP-FPM restarts.
7. **Login rate limit**: 6 failed attempts per username or IP in 15 minutes, then a 15-minute wait. Attempts are stored in `chroma_login_attempts` and pruned after a day.
8. **Easy/Expert mode is stored on the user row** (`ui_mode`) and mirrored in a one-year cookie (`chroma_mode`) so the shared lab PC remembers it before anyone signs in. Theme (light/dark/system) is a cookie plus localStorage; it is a device preference, not a user one.
9. **Wizard state lives in the PHP session** under `_wizard.{key}`; the review screen is the only place that commits. Switching to Expert mid-wizard carries the entered values as query-string defaults where the Expert page supports them.
10. **Help pages are markdown files** in `resources/help/`, rendered with Parsedown in safe mode, so the lab can edit them without touching PHP.
11. **Seeded data is reference only.** Prefix `next_number` values from the spec table are seeded, but the legacy import overrides them with max-in-use + 1 unless an admin has already set something higher.
12. **Codes are dated by the lab's calendar day** (`America/Chicago`), not UTC, because `date_assigned` is a plain date shown unshifted in the cross-reference. Datetimes stay UTC.
13. **A project item holds at most one live E# and one live sell number.** Assigning a second code to an item is refused inside the assignment transaction (so no number is consumed); void the first one if it was a mistake. This stops a double-click or a retried request from orphaning a reserved number.
14. **Counters may move down as well as up, but never onto a used number.** The spec's rule is `max(MAX+1, next_number)`, so lowering an accidentally high counter back to the number after the last one used is allowed; both directions are audited.
15. **Historical prefix spellings are handled in search, not in the parser.** `UVV` finds `UVVL` codes and the original spelling in `legacy_text` is searchable, while the parser stays literal so the importer's "map UVV to UVVL" switch keeps working.
16. **Fulltext searches leave out words InnoDB does not index** (shorter than three characters, such as `UV`, and stopwords such as `for`); requiring them would return nothing.
17. **Routes may require any one of several permissions** (`->anyPermission(...)`), used where either assign permission unlocks a page.
18. **Dev and test scratch files are per user** (`/tmp/chroma-test-<uid>`), so a suite run as root never blocks the updater's run as the `chroma` user.


## Module D decisions — code lookup, logs, code pages, quick assign, void, link, manual entry

1. **Lookup results are grouped by product.** A product is an E number with every sell number linked to it, or a sell number that has no E number yet. The search is a UNION of indexed probes (exact normalized sell number, `sell_number_normalized LIKE 'Y1000%'`, E number exact + "starts with these digits" ranges, `number = n` for an all-digit query, prefix code, `legacy_internal_code`, FULLTEXT on both description columns, customer ids from the indexed customer name) that yields product keys; the keys are grouped, ranked (exact match first), paginated in SQL, and only then are the page's rows loaded. No `LIKE '%…%'` anywhere.
2. **"Starts with these digits" for E numbers** means E63 → E63, E630–E639, E6300–E6399 … (one BETWEEN range per extra digit), never everything in between. `LookupApiController::upperBound` (not this module's file) uses a single open range, which makes E6374 also match E9102 — see `docs/requests/D.md`.
3. **An all-digit query** (`6374`) searches both E numbers and sell numbers with that number under any prefix; the sell probe scans the `(prefix_id, number)` index, not the table.
4. **A query that is only letters** (`Y`, `uv`) and equals a prefix code lists that prefix, lowest number first (handy for "browse Y"). Browsing a prefix without a term (`/codes?prefix=Y`) does the same.
5. **Multi-word queries** (`T2449 Blister`) try the whole string and the first word as a code, and the whole string as fulltext words; the union of the readings is returned.
6. **Voided codes stay visible** in lookup and logs, greyed with a red "Voided" badge; "Active only" / "Voided only" filters narrow the list. A product card is greyed only when its E number is voided or every one of its sell numbers is.
7. **Logs order:** a prefix log is by number descending (newest number first, suffix variants together); the E log by number then version descending. Both support search within the log, active/voided filters, a date range (Expert), CSV/XLSX export (capped at 20,000 rows) and server-side pagination.
8. **SDS link pattern:** `sds_base_url` + `/` + `E` + base number (`https://sds.example.com/E9102`). Versions share the base E number (`E6374-10` → `…/E6374`). If the base URL contains `{E}` (the placeholder Admin → System documents and validates) or `{code}`, the E number is substituted there instead (`http://sds.precisionink.local/sheet/{E}` → `…/sheet/E9102`), so an SDS system with a query-string lookup works without code changes. The link is only shown when the setting is non-empty.
9. **Notes and description edits** on code pages are allowed to anyone with either assign permission (`codes.assign_sell` or `codes.assign_internal`), and are audited as `code.notes` / `code.description` with before/after snapshots. Unchanged saves write nothing.
10. **The quick-assign operation lives in `src/Domain/Codes/QuickAssign.php`** (a new file beyond the owned list; needed so the wizard, the Expert page and the tests call one operation). It validates the request shape; counters, prefixes, suffixes and reasons are checked by `CodeAssigner`. Everything happens in one `Db::transaction`, so a refused sell number rolls back the E number assigned a moment earlier.
11. **A reason is required when adding a sell number to an existing product** (alias); it is optional for brand-new products. The description defaults from the product; the customer defaults from the product unless another is chosen.
12. **A product that already has an E number cannot get another one** from quick assign — the message tells the user to choose a sell number or pick "brand-new product". A sell number without an E number can get one (and the existing sell number is linked to it, audited as `code.link`).
13. **Permissions for quick assign:** the page/wizard opens with either assign permission; the operation refuses (403) if the chosen kind of code needs a permission the user lacks. The forms only offer the kinds the user may assign.
14. **Typeahead reuse:** linking and manual entry accept either an E number or any sell number of the product from `/api/codes/search`; a sell number resolves to its E number. A sell number with no E number is refused with a plain message.
15. **Easy ↔ Expert carry-over:** the wizards' "Expert" switch builds `/assign?…` or `/codes/manual?…` URLs with the entered values; the Expert pages pre-fill from the query string. The Expert pages redirect Easy-mode users to the wizard unless `?expert=1` is present (used by those links).
16. **Exports are audited** (`code.export`, with the query/log and row count) so it is visible when the cross-reference was downloaded.
17. **Retired prefixes** show in the logs index under their own heading and in the lookup's prefix filter, but not in the "browse a prefix" chips or assign forms.
18. **The "already linked" case** on the Expert link form is a no-op with an info toast rather than an audit entry.
19. **Manual entry has its own small operation, `src/Domain/Codes/ManualEntry.php`** (a second file beyond the owned list, for the same reason as #10: one operation for the Expert page and the wizard). Before calling `CodeAssigner::manualSell/manualInternal` it refuses, in plain words, what the database could not store — sell numbers over 6 digits, E numbers over 6 digits, versions over 20 characters (`CodeFormat` saturates long digit strings at `PHP_INT_MAX`, which used to surface as an HTTP 500 "out of range" PDO error) — and a code that is already used, naming it the way it is displayed everywhere else (`BN0777 is already used by E6374`, not `BN777`). The wizard runs the same checks on the code step so the user hears about it before the details step.
20. **Reason "Other" always comes with a "Say why" box.** Both manual-entry shells show `reason_text` when the reason is Other (Expert: Alpine `x-show`; Easy: the generic `codes/wizard-details` step template, which supports a `show_when` key on a field spec) and require it only then, matching quick assign.
21. **The void wizard says up front when a code is already voided** (one informational screen with a way back, no reason asked, no commit possible) instead of asking for a reason and refusing on the review screen. The detail pages hide the Void button; the URL is still reachable from history or bookmarks.
22. **Source is shown in plain words everywhere** (`CodeSearch::sourceLabel`: "Assigned in Chroma", "Imported from the spreadsheets", "Entered by hand") — lists, pages and exports alike; the raw `assigned`/`import`/`manual` values never reach the screen.
23. **`db/migrations/0040_sell_number_index.sql` adds `ix_sell_number (number)`** so the all-digit lookup probe (`6374` → Y6374, BK6374 …) hits an index; every key on `chroma_sell_numbers` started with `prefix_id`, so that probe scanned the table (EXPLAIN type=ALL). Verified with EXPLAIN (`ref`, `ix_sell_number`, `Using index`) and a test.
24. **Both shells collect the same fields:** the quick-assign wizard now has Notes (like `/assign`), the manual-entry wizard collects the vendor's code (like `/codes/manual`), and the Expert pages pre-fill all of them from the wizard's "Expert" switch.
25. **The E-number page at phone width** uses `minmax(0, 1fr)` columns and `min-width: 0` on the stacks/cards so the sell-numbers table scrolls inside its own `.table-wrap` instead of pushing the page past the viewport.
26. **The Expert manual-entry form keeps what was typed after a server-side refusal** (`old()` wins over the query-string defaults). Before, a refusal such as "say why" or "already used" reloaded the form with the code and description blank. Found while verifying #20.


## Decisions — module F (installer, updater, helper, backups)

1. **Dev dependencies stay installed in production.** `install.sh` runs `composer install` *with* `require-dev` (PHPUnit) instead of `--no-dev`, because the updater runs the test-suite on the server before switching versions. PHPUnit is never loaded by a web request (nothing in `src/` references it, and only `public/index.php` is reachable through nginx), so the only cost is ~10 MB on disk. The alternative (a throwaway copy of the tree with dev deps per update) doubles the composer work and the disk, for no safety gain.
2. **Prompts come first.** The admin and network questions are asked right after the OS check, before `apt`, so the operator can walk away during the slow steps. The network change itself is still applied last.
3. **First run is resumable.** A marker file `/etc/chroma/installed` is written at the end of a successful first run. If `config.env` exists but the marker does not (the install stopped half-way), the next run resumes the first-run steps and keeps the password already in `config.env` instead of switching to update mode. Every first-run step is idempotent, so "fix the problem and run the same command again" is always correct.
4. **After `git pull`, the updater re-executes the NEW `install.sh`** (`--continue-update <old-commit>`), so steps added to the installer in the new version run during the same update. `chroma-update` is therefore a thin wrapper around `/opt/chroma/install.sh` and never needs to change.
5. **Rollback = `git reset --hard <old>` + `composer install` + reload.** Migrations are not undone: they are additive (`IF NOT EXISTS`) and the old code ignores new columns. The message says so and points at the pre-update backup.
6. **The updater ignores untracked files** in `/opt/chroma` (`git status --porcelain --untracked-files=no`) and refuses only on modified tracked files. Untracked files (an operator's notes, a stray log) cannot break a fast-forward merge.
7. **`/etc/chroma/config.env` is owned by `chroma`, mode 600**, not root-owned, because the Admin → CMS connection screen writes credentials into it and `chroma-helper set-network` updates `APP_URL`. Its contents are never rewritten by the installer; ownership and mode are re-asserted on every run.
8. **The app user gets a clean environment** (`runuser … env -i` with HOME, PATH, COMPOSER_HOME, CHROMA_CONFIG and, when set, the `*_proxy` / CA variables). Root's environment must not leak into composer/git/php runs.
9. **nginx listens on IPv4 only** (`listen 80 default_server`, no `[::]:80`): nginx refuses to start on a server with IPv6 disabled when `[::]:80` is listed, and the lab network is IPv4.
10. **pdo_sqlsrv archives are downloaded with curl and installed from the local file.** `pecl install sqlsrv` uses its own HTTP client which fails behind some proxies (seen in the build container: "426 Upgrade Required"); `curl` honours the system proxy settings. On failure the half-enabled extension is removed again so `php` does not print warnings on every call. The result goes into the `cms_driver_status` setting after `bin/migrate`.
11. **Sudoers allows only `/usr/local/sbin/chroma-helper`**, not `chroma-update`: the helper's `update` command runs the updater as root itself. One entry point, one place that validates arguments.
12. **`set-network` checks that the gateway is inside the subnet** and refuses `/31`, `/32`, loopback and the server's own address as gateway: a typo here would lock the lab out of the server, and `netplan generate` does not catch it.
13. **`set-network <iface> dhcp`** was added to the helper contract on request of the Admin → Network module (docs/requests/admin-system.md #3). It writes `dhcp4: true` for that interface.
14. **Backups**: `mysqldump --single-transaction --quick --triggers` (no `--routines`: the app has none and that flag needs extra privileges on MariaDB), gzip level 6, files named `chroma-db-YYYY-MM-DD_HHMMSS.sql.gz` in local time so an operator can read them; attachments go into a separate tarball; both mode 600. Pruning is by file age (`-mtime +30`), so copies the operator keeps elsewhere are untouched.
15. **Timers**: backup at 02:17 and CMS sync at 03:17 local time with 10 minutes of random delay and `Persistent=true` (a missed run happens at next boot). The CMS sync unit has `ConditionPathExists=/opt/chroma/bin/cms-sync`, so it is harmless until that tool ships.
16. **Database names and the DB user are overridable** (`CHROMA_DB_NAME`, `CHROMA_DB_USER`, `CHROMA_TEST_DB_NAME`) so the installer can be tested on a machine that already has a `chroma` database, and so a future shared database server can be used. The test database is `<name>_test` by default.
17. **`bin/uninstall` keeps `/etc/chroma/config.env`, the attachments and the backups** (not only the database) unless `--purge`: the config holds the database password needed to reuse the kept database. The netplan file is never removed.
18. **Logs**: nginx access/error logs go to `/var/log/chroma/` too (SPEC §9 "logs to /var/log/chroma, rotated"); one logrotate stanza covers everything with `su chroma chroma`.

### Added after the review (2026-10-27)

19. **`/opt/chroma` is owned by root and read-only for the web-app user.** git and composer run as root (`COMPOSER_ALLOW_SUPERUSER=1`, cache in `/var/cache/chroma/composer`); PHP (migrate, create-admin, the test-suite, backups) still runs as `chroma`. The `chroma` user can write only `/var/lib/chroma`, `/var/log/chroma`, `/var/backups/chroma` and `/etc/chroma/config.env`. Reason: `chroma-helper update` makes root execute `/opt/chroma/install.sh` and copy `bin/*` and `deploy/*` into system locations; when the web app owned those files, any code-execution bug in a web page was a root shell. Belt and braces: `chroma-helper update`, `chroma-update` and `install.sh` itself all refuse to run or install a tree that is not root-owned or is group/world-writable (`assert_not_app_writable` / `assert_tree_root_owned`), with the exact `chown` command to fix it. The one chroma-writable spot inside the tree is `tests/fixtures/legacy`, which the importer test writes (nothing root runs lives there; a request to move it to the temp dir is in docs/requests/F.md).
20. **The test-suite runs on the live checkout, after the fast-forward merge.** README and the help page now say so honestly: during the 2–3 minutes of tests the new code is what nginx serves, and a failure reverts it. Testing in a separate checkout first (git worktree + a second composer install) was considered and rejected for v1: double disk and composer time, and the migrations would still have to run on the real database before the tests mean anything. Operators are told to update at a quiet moment.
21. **The complete PHPUnit output goes to `/var/log/chroma/phpunit-<date>.log` (root 0640)**; the screen and install.log show only the last 40 lines plus the file name, and the red rollback box names the file. The lines that explain a failure (forked-child errors, PHP warnings) are printed early and were lost before.
22. **`bin/uninstall` is also installed as `/usr/local/sbin/chroma-uninstall`** and kept after a keep-mode uninstall, so `sudo chroma-uninstall --purge` works once `/opt/chroma` is gone. A purge removes it too.
23. **A generated admin password is printed to the screen only** (file descriptor 3, saved before the `tee` into install.log); the log line says "shown on the screen only". install.log is 0644 root so other server administrators can read it, and it must never carry a credential.
24. **Static-network answers are validated at prompt time with the same rules as `chroma-helper set-network`** (gateway inside the subnet, not the server's own address, no /31–/32, no loopback, interface exists). A netplan refusal at the very end is no longer fatal: the install marker is already written, the message shows the exact `chroma-helper set-network …` command to retry, and Chroma stays reachable at the old address.
25. **Everything run as the app user gets `TMPDIR=/var/lib/chroma/tmp`** (0700, chroma). The suite writes fixed names under `sys_get_temp_dir()`; if someone ever ran it as root in `/tmp`, every later update as `chroma` failed on `Permission denied`.
26. **`list-backups` lists both the database dumps and the attachment tarballs** so Admin → System can download either; `backup` still prints only the dump path (the contract).
27. **Error helpers take the message as `$1`**; `die "<msg>" <code>` and `fail "<msg>" <code>` no longer append the exit code to what the Admin screens show.


## Decisions — Module A: Admin prefixes, suffixes, sequences

1. **One domain class, `src/Domain/Codes/PrefixAdmin.php`**, holds every admin rule for prefixes, suffixes and the two shared sequences. The Expert forms (`PrefixesController`, `SuffixesController`, `SequencesController`) and the Easy wizard (`AddPrefixWizard`) call the same methods; no validation lives in the shells. Counter moves delegate to `CodeAssigner::setPrefixNextNumber` / `setInternalNext` so the FOR UPDATE locking and messages stay in one place. The project-number counter is the one new piece of locking code (`setProjectNext`), written the same way.
2. **Prefix/suffix letters are locked once a code carries them.** Renaming would change product codes printed on cans and orders. The edit form shows the letters disabled with the reason; the domain method refuses with the same explanation. A prefix with no codes can still be renamed (handy right after a typo).
3. **"Last used" shows the number only**, formatted with the prefix's `min_digits` (`Y1715`), never a suffix: the suffix belongs to the individual code, the counter does not know about it. "Next number" is `max(MAX(number)+1, next_number)`, the same rule `CodeAssigner` applies.
4. **Retire / un-retire are allowed on every prefix**, including inherited and legacy ones, and are refused only when the prefix is already in that state. `retired_at` / `retired_by` are set on retire and cleared on un-retire. Both are audited (`prefix.retire`, `prefix.unretire`) with before/after snapshots of the admin-editable columns.
5. **Deactivating a suffix** keeps the prefix→suffix links; the suffix just stops appearing as an option (CodeAssigner already refuses inactive suffixes). Switching it back on restores it everywhere without re-ticking.
6. **Moving a prefix counter needs `admin.sequences` as well as `admin.prefixes`** (the permission catalogue says "Set next numbers … or prefix counter"). The form is hidden without it and the route checks both.
7. **Inherited / legacy tags are badges only.** They are read from the existing `tag` column and are not editable here; they do not change behaviour.
8. **Lists use server-side pagination (50 per page) even though there are ~32 prefixes**, to keep every list consistent with the rest of the app; search matches the start of the code or name and anywhere in the description.
9. **The prefix admin controllers redirect with `$this->redirect()` rather than `Controller::done()`** because `WizardController::done()` currently clashes with `Controller::done()` (see docs/requests/admin-codes.md); this module is unaffected whichever way the lead resolves it.
10. **No schema change was needed.** Everything fits the existing `chroma_code_prefixes`, `chroma_code_suffixes`, `chroma_code_prefix_suffixes` and `chroma_sequences` tables.

### Review fixes (round 2)

- **Links to switched-off suffixes survive prefix edits.** `PrefixAdmin::updatePrefix` now merges any existing link to an inactive suffix back into the posted set, so an unrelated edit (description, digits…) can no longer unlink a suffix that is currently off. The edit form shows such suffixes ticked and greyed with "(switched off)" and explains how to remove the link for real (switch on → untick → switch off). Rationale: the brief says switching a suffix off leaves everything else untouched, and the form only offers switched-on suffixes.
- **Counters: copy now matches behaviour.** CodeAssigner/PrefixAdmin accept any value above the highest number already used, including a lower unused value (undoing an over-generous skip). Rather than refuse lower values (which §4 does not require and which would make a mistaken skip permanent), the page copy, wizard hint and help page now say "never to a number that has already been given out" and name the floor.
- **Easy and Expert use the same words on the number-format step.** `AddPrefixWizard::validateStep('format')` calls the new `PrefixAdmin::formatProblems()` instead of the generic numeric validator.
- **Failed save keeps unticked suffixes.** `_fields.php` treats the presence of `old('label')` as "a form was submitted" and then uses `old('suffix_ids')` (or none) instead of the saved set.
- The "see the log" link goes to `/codes/logs/{PREFIX}` (the per-prefix route), the 404 text no longer says "id"/"merged", dialogs say "No codes have been given out under it yet" when the count is 0, and a `code` error is shown under the locked code field.


## Decisions — module E2 (Admin: System, Network, CMS, Settings, Audit)

1. **CMS connection is split in two stores.** Host, port, database, username and password live only in `config.env` (`CMS_HOST`, `CMS_PORT`, `CMS_DATABASE`, `CMS_USER`, `CMS_PASS`) written through `Config::write`; the schema mapping (`cms_customer_table`, `cms_customer_id_column`, `cms_customer_name_column`, `cms_customer_active_column`, `cms_customer_filter`), the on/off flag and the sync results live in settings. The password is never read back into a page; the screen shows "set" / "not set" and a blank password field keeps the saved one.
2. **The customer query is built only from the mapping**, with identifiers bracket-quoted; the filter is a `WHERE` fragment validated to refuse semicolons, comments and data-changing keywords. The connection opens with `ApplicationIntent=ReadOnly`. Chroma never writes to CMS.
3. **CustomerSync matching order**: CMS id, then normalized name (`Customers::findByName`). A name match adopts the CMS id so it is matched by id afterwards, but keeps the hand-typed name and `source`. Only `source = 'cms'` rows are renamed or deactivated. Deactivation of missing CMS customers is behind the `cms_deactivate_missing` setting (default off) and is skipped entirely when the source returned no rows, so a broken query can never deactivate everyone. Nothing is deleted.
4. **Every sync is recorded** in `chroma_cms_sync_runs` and as an audit entry (`cms.sync`), including failures; `cms_last_sync_at` / `cms_last_sync_result` always reflect the latest attempt. `bin/cms-sync` exits 0 quietly when the connection is off and 1 when a sync fails (so the systemd timer shows the failure).
5. **Update runs as a detached background job.** `Updates::start` launches `sudo -n chroma-helper update [branch]` under `nohup setsid`, appending to `<LOG_PATH>/jobs/update-<id>.log` and ending with `__CHROMA_JOB_EXIT__ <code>`. PHP-FPM is reloaded half way through an update, which would kill a streaming request, so the browser polls `GET /admin/system/update/log?job=…&from=<offset>` (JSON: new complete lines, new offset, done, exit) every 1.5 s and keeps retrying through the reload.
6. **Backup downloads** accept a bare file name only (`[A-Za-z0-9][A-Za-z0-9._-]*`, a backup extension, no dot-files); the path is resolved with `realpath` and must stay inside the backup directory. The listing comes from the helper's `list-backups` when installed, otherwise from scanning the directory, and never shows anything outside it. The directory can be overridden with `BACKUP_PATH` in config.env (tests use a temp dir).
7. **Network validation** is strict and in the domain class: IPv4/CIDR (1–32) that is not loopback/reserved/multicast nor the network or broadcast address, an IPv4 gateway inside that network, one to three IPv4 DNS servers, an interface name matching `[a-zA-Z][a-zA-Z0-9_.-]{0,15}`. The mirror (`network_mirror` setting) is written only after the helper accepted the change, so it never shows settings that were not applied.
8. **DHCP** is offered in the form and wizard and sent to the helper as `set-network <iface> dhcp`; see docs/requests/admin-system.md, since the helper contract only lists the static form today. If the helper refuses, the screen shows its message and nothing changes.
9. **Audit diffs** are computed from the before/after JSON in `AuditController::diff`: changed fields first, at most 5 (3 for creates) shown inline, the rest folded in a `<details>`. Export is capped at 50,000 rows.
10. **Settings and Audit log live under System** (sub-navigation on all three pages) because `AdminController::areas()` cannot be edited by this module; see the request file.
11. **Time zones** offered are the seven US zones plus UTC (`AppSettings::TIMEZONES`); the SDS link accepts `{E}` as the placeholder for the E number.
12. **NetworkWizard** lives in `src/Http/Controllers/Admin/NetworkWizard.php` (next to its controller) because `src/Http/Wizard/*` is owned by the core.

### After the independent review (fix pass)

13. **DHCP refusals are translated, not hidden.** The repo's `bin/chroma-helper` now supports `set-network <iface> dhcp`; an older installed helper still refuses with an argument-count message. `Network::refusalMessage()` turns that one case into plain words (older helper, nothing changed, re-run install.sh or pick a fixed address). We kept the DHCP option visible rather than removing it, because the helper that ships with this version supports it; the Expert radio text says an older helper refuses it.
14. **CMS passwords with `"` or `\` are refused up front** rather than patching `Config::load()` (core, not ours). `CmsConnection::validate()` says why in one sentence; `save()` additionally re-reads config.env and refuses to keep a password that does not come back exactly as typed. Request #6 asks for the core un-escape so the rule can be relaxed later.
15. **Turning the CMS connection on requires a password** that is already saved or typed in the same submit, and cannot be combined with "Remove the saved password". Before this, the connection could be switched on with no password and every nightly sync failed. The checkbox help text now matches the rule.
16. **Audit note search uses a FULLTEXT index** (migration `0035_audit_note_fulltext.sql`, `MATCH … AGAINST … IN BOOLEAN MODE`, every word required and prefix-matched, words under three characters dropped because InnoDB does not index them). A number typed in the box still matches the row id exactly. No `LIKE '%…%'` on the audit table any more.
17. **Audit log on phones is a stack of cards** (below 640 px): each entry shows when / by / action / table / change with the before-after diff as a small table inside the card, instead of a sideways-scrolling table with very tall rows. Pure CSS in `system-admin.css` keyed on `data-label` attributes; the desktop table is unchanged.
18. **Backup downloads above 8 MB are streamed** with `readfile()` from `SystemController::downloadBackup` (same headers as `Response::file`), smaller ones still go through `Response::file`. Prevents a 500 once backups include attachments and exceed PHP's memory_limit.


## Decisions — module E1 (Admin: users & groups, lists, project types, customers)

1. **Customer admin operations live in `src/Domain/Lists/ListAdmin.php`** (add, rename, activate, merge) rather than a new
   `CustomerAdmin` class, because the module's file ownership does not include a customers domain file and
   `Domain/Customers/Customers.php` (lookup / find-or-create shared with import and CMS sync) must not change. The spec treats
   customers as one of the admin "lists" under the `admin.lists` permission, so the grouping is defensible. Easy to split later.
2. **Only an Administrator can promote someone to Administrators.** The spec only forbids *removing* / *deactivating* an
   administrator by a non-administrator; without the symmetric rule anyone with `admin.users` could add themselves to
   Administrators and then do both. `UserAdmin::assertMayChangeAdminMembership` enforces both directions.
3. **Administrators always hold every permission.** The seeder re-adds all keys on every run anyway, so the permission form for
   that group is shown read-only and `GroupAdmin::setPermissions` refuses changes with an explanation. Name is fixed too
   (`Auth::isAdmin()` checks the name); description and membership can be edited.
4. **Temporary passwords are "Word-Word-Word-NN"** (e.g. `Amber-Harbor-Pilot-42`), generated by `UserAdmin::generatePassword()`.
   Readable over the phone and typeable on the lab PC; always passes `Auth::passwordProblem`. Shown exactly once: on the wizard
   success screen, or on the user page right after create/reset (held in the session under `_shown_password` and pulled on first view).
5. **Resetting a password or deactivating signs the user out everywhere** by deleting their rows in `chroma_sessions`
   (a reset keeps the current session when an admin resets their own).
6. **Usernames are stored lowercase and never change** (the logs identify people by them); display name, email and initials can change.
7. **Simple list entries (ink series, coatings, substrates) can be hard-deleted only when nothing references them**
   (`chroma_project_items.*_id` and `chroma_projects.default_*_id`); otherwise `ListAdmin::delete` refuses with a message that
   points to Deactivate. The UI only shows Delete when the usage count is 0.
8. **Customer merge moves `chroma_projects.customer_id`, `chroma_internal_codes.original_customer_id` and
   `chroma_sell_numbers.original_customer_id`**, deactivates the duplicate (never deletes it), appends a "Merged into …" line to
   its notes, and writes two audit rows (on the kept and the merged-away customer). If the duplicate carried a CMS id and the kept
   customer has none, the CMS id moves to the kept customer (and its source becomes `cms`) so the sync keeps matching the right
   row instead of re-creating the duplicate. The kept customer must be active.
9. **Stages and item statuses get a slug code from their label** (`uniqueCode()`, suffixed `_2`, `_3` … on clashes within the
   type) so the lab never has to type codes. Reordering renumbers the whole scope 10, 20, 30 … so orders stay unambiguous.
10. **A status marked "not finished" cannot be a "success"** (`is_success` is cleared), and at least one active not-finished status
    must remain in each list so new items have a starting status. Stages / statuses in use can be deactivated but not removed.
11. **"Customize for this type" copies the shared status list** into type-specific rows; "Use the shared list again" deletes
    them, but only while no item carries one of them. The shared list itself is edited at `/admin/item-statuses`.
12. **A project type can be deactivated unless it is the only active one**; its code never changes after creation.
13. **One schema addition: `db/migrations/0050_customers_fulltext.sql`** adds a FULLTEXT index on `chroma_customers.name_normalized`
    (idempotent `CREATE FULLTEXT INDEX IF NOT EXISTS`). Everything else uses `db/migrations/0001_schema.sql` as is.
14. **Easy vs Expert in lists**: Easy mode shows fewer columns (no last sign-in / password flag / notes / sort) and 25 rows per page;
    Expert shows everything and 50 rows. Behaviour is identical.
15. **Customer search never uses an infix LIKE.** `ListAdmin::customers()` joins a derived table made of three indexed lookups
    (`name_normalized LIKE 'q%'`, `cms_customer_id = q`, and `MATCH (name_normalized) AGAINST ('+w1* +w2*' IN BOOLEAN MODE)`),
    so "labels" still finds "ACME Labels, Inc." as the CMS list grows. Words shorter than 3 characters are not in the FULLTEXT
    index (`innodb_ft_min_token_size`), so they are left out of the MATCH; a search made only of short words is a prefix match.
    The derived-table form was chosen because an OR across a FULLTEXT and a B-tree index makes MariaDB scan the whole table.
16. **You cannot remove yourself from the Administrators group** (`UserAdmin::assertMayChangeAdminMembership`), mirroring "you
    cannot deactivate yourself": an Administrator who removed themselves would lose every admin screen on the next request with
    no way back. Another Administrator can still remove them. The last-admin rule is checked first, so its message wins when both apply.
17. **A refused inline save reopens the same row.** The list, stage and status editors redirect back with `?edit={id}` (or
    `edit_stage=` / `edit_status=`), the typed values in the row's inputs and the message under them, instead of landing in the
    "Add" box at the top of the page.
18. **Phone layout for the list editors**: tables marked `table-stack` (lists, stages, item statuses) render each row as a small
    card below 640px with the column name in front of each value, so the status and the Edit/Deactivate buttons are never hidden
    behind a horizontal scroll. Desktop and tablet layouts are unchanged.


## Decisions — Module B, legacy spreadsheet importer

Choices made where SPEC.md §2.3 / §5 left room. Newest at the bottom.

1. **Same three-step flow in Easy and Expert mode.** Upload → dry run → commit is sequential by nature, so the import does not use the generic `Wizard` framework (which cannot carry file uploads and keeps state in the session). It is a plain controller at `/admin/import` whose screens show a step indicator in both modes; Easy mode only enlarges the primary buttons and hides a few table columns. No `/wizard/import` key is registered.
2. **Dry runs are recorded in `chroma_imports`** (`dry_run = 1`, status `dry_run`), with the uploaded files' server paths in `files_json` and the report in `summary_json`/`log_text`. The review screen renders from that record, and the commit re-reads the stored files and recomputes the plan rather than trusting anything kept in the session. After a commit the dry-run record's status becomes `committed`; re-running the dry run with a different UVV choice marks the old one `superseded`. No new columns were needed, so there is no migration.
3. **Uploads live under `FILES_PATH/imports/<timestamp>-<random>/`** and are kept after the commit so a past run can be re-examined. Max 25 MB per file, three files per upload, `.xls`/`.xlsx` only.
4. **File order is normalised**: the cross-reference is always processed first, then the X log, then the UV log, whatever order they were uploaded in. The cross-reference defines a code; the logs fill in blanks (comments become notes). The same code appearing in two sheets is a "repeat", not a duplicate.
5. **Duplicates are flagged wherever the E number disagrees** (after review): within one sheet (also for a different description), between two sheets of the same run (cross-reference vs X log), and against what Chroma already holds (a catch-up sheet that puts an existing sell number under another E number). The kept side — the first row, or Chroma's own row — is never touched, not even its empty fields; the other row goes to `chroma_import_issues` with the full raw row, `kept_code`, `kept_where` and `kept_internal`. A repeat with the same E number (or no E number on one side) still merges silently: a log row fills the blanks of a cross-reference row.
6. **A second row with the same E number and a different sell number is not an issue** — it is the relabel / alias case from §2.1, and the second sell number is linked to the same E number.
7. **E numbers named only in the code logs are created from the log row** (description from the X/UV code), so the sell number keeps its link. The cross-reference should normally hold them already; when it does, the log row only fills blanks.
8. **Rows with a code but no description get the placeholder** `No description in legacy sheet` (prefixed with the related code where there is one), because `CodeAssigner` refuses an empty description. The importer treats that placeholder as "empty" so a later sheet can replace it.
9. **"Fill only empty fields" treats `resale = 0` as empty**, so a resale flag from the sheet is applied to an existing E number that never had it set. A description, notes, customer, vendor, date or E-number link is filled only when Chroma's value is blank.
10. **Unknown suffixes are issues, not new suffixes.** Suffix codes are small and admin-managed; creating one from a possible typo would make it assignable. Known suffixes found per prefix are added to `chroma_code_prefix_suffixes` (audited) as §2.2 asks.
11. **Unknown prefixes that parse are created as retired prefixes** directly in `chroma_code_prefixes` (label "`XX` (retired)", `min_digits` from the longest number seen, tag `retired`, audited `prefix.create`). `CodeAssigner` only owns code rows, not prefixes.
12. **Rows without a date keep no date.** `CodeAssigner` defaults `date_assigned` to today when the key is absent, so after the run the importer sets `date_assigned = NULL` on the rows it created from undated sheet rows. (A request to accept an explicit null is in `docs/requests/import.md`.)
13. **Issue de-duplication is by content, not row number.** Each issue carries a fingerprint (type, sheet, code, internal code, description, comments, customer) in `raw_json`; an import skips writing an issue whose fingerprint already exists, open or resolved. So a catch-up sheet with a different header row does not re-list the same duplicates.
14. **The whole commit is one transaction.** A row refused by the code rules becomes a `refused` issue and the run continues; any other failure rolls everything back and the run is recorded as `failed`.
15. **Counters after a commit** use `GREATEST(current, max + 1)` semantics with an audit entry when they move. `manualSell` already bumps a prefix counter as it inserts, so in practice only the E sequence changes at the end.
16. **"Enter corrected code" on an issue requires `codes.manual_entry`** in addition to `admin.import`, matching the rule that entering a specific code by hand is its own permission. Merge and discard need `admin.import` only.
17. **Performance**: 8,100 + 500 + 400 rows import in about 40 s over TCP and about 22 s over the MariaDB unix socket; almost all of it is `CodeAssigner`'s per-code round trips (~2 ms per code). The importer preloads prefixes, suffixes, customers and every existing normalized code, so its own cost is ~1.5 s. The PHPUnit timing test uses 3,000 rows against a proportional budget to keep the suite quick.
18. **Fixtures are generated**, not hand-made: `tests/fixtures/make-legacy-fixtures.php` writes an `.xls` cross-reference (header on row 3), the two `.xlsx` logs (UV header on row 2) and a catch-up sheet; it covers every edge case named in §2. The suite regenerates them if missing.
19. **Known issues are reported, not re-counted** (after review). `plan()` preloads every recorded issue fingerprint; an issue already on the list (open or resolved) is marked `known`, shown as "already on the list" and excluded from "Issues to expect", so the dry run's count equals what the commit writes.
20. **A dry run can be committed once, and only one import runs at a time** (after review). `commit()` takes a MariaDB advisory lock (`GET_LOCK('chroma_legacy_import', 0)`) and, when given the dry-run id, row-locks the `chroma_imports` row and moves it `dry_run → committing → committed` (back to `dry_run` on failure so it can be retried). A second tab or the CLI gets a plain-language refusal instead of a `1062 Duplicate entry` failure; the one duplicate-key error that could still slip through is translated into plain language.
21. **A bare year is not a date.** `SpreadsheetReader::parseDate` only accepts Excel serials between 1950 and 2100 (18264–73415), so "2019" typed in the Date column is listed under *Dates that could not be read* instead of becoming 1905-07-11.
22. **Merge is only offered for sell numbers Chroma already holds** (the kept code of a duplicate, or the row's own code): an unreadable or unknown-suffix row no longer offers "merge into" its own E number.
23. **A corrected code does not inherit the sheet's typo as `legacy_text`**; the typo is quoted in the notes only. The customer of a corrected row is created inside the same transaction as the code, so a refused code leaves nothing behind.
24. **Working through one run's issues keeps the run filter**: `?import_id=N` travels from the done page through the list, the issue page and the resolve actions to the next open issue of that run.
25. **Performance stays ~30–40 s for a full-size commit** on this box (reviewer: 32 s). The cost is CodeAssigner's per-code round trips (`docs/requests/import.md` #2/#3); the one-transaction design (decision 14) means the counters are locked for the whole run, which is acceptable for a one-off at cutover when nobody is assigning. Splitting the commit into chunks would trade that for partial imports on failure; not done.


## Decisions — Projects module (C)

1. **Project numbers** come from `chroma_sequences.project_number` locked with `SELECT … FOR UPDATE` inside the create transaction; the number used is `max(MAX(project_number)+1, next_value)`, same rule as codes. One shared sequence for every type (R&D included); the type shows as a badge (SPEC §11 default, pending Matt's answer in QUESTIONS #7).
2. **R&D projects carry the internal customer** "Precision Ink R&D" (setting `rnd_customer_name`, created on demand by `Customers::internalRndId`) rather than a NULL customer, so codes assigned from R&D items get an `original_customer_id` and the list shows something sensible. Types with `has_customer = 0` never ask for a customer.
3. **Visibility of confidential projects**: lead (`assigned_user_id`), team members, the person who created it, members of the `R&D` group, Administrators and anyone with `projects.view_confidential`. Enforced in the list query (`Visibility::sqlFilter`) and on every `/projects/{id}/…` route (`ProjectController::loadProject`) as a **404**, so existence is not leaked. `created_by` was added to the spec's list so the creator cannot lock themselves out.
4. **Auto-complete**: after any item status change (and after an item is moved away), a project completes itself when it has at least one item and every item's status has `is_done = 1` (matched / approved / rejected / not needed). Manual complete, cancel (with a reason) and reopen are separate operations with `projects.complete`. Completion sets `date_completed = today()` in the display timezone.
5. **Progress wording**: "N of M matched" on color matches, "N of M done" on every other type (`Projects::progressWord`). The only type-code check in the module; everything else comes from `ProjectTypes`.
6. **Items that hold a code are never hard-deleted** (`Items::remove` refuses with a plain-language message pointing to "Not needed" or voiding). Items without codes can be removed; the audit log keeps the row snapshot.
7. **Existing-product items** are linked through the code picker (`/api/codes/search`, result ids `E{id}` / `S{id}` passed as `existing_ref`). Picking a sell number also links the E# behind it; the description defaults from the code. No code is ever assigned by the picker.
8. **Substrate** is free text with a datalist of the admin list; typed text that matches a substrate name (case-insensitive) also sets `substrate_id`. Same for the project default.
9. **Batch assignment** runs one `CodeAssigner` transaction per item and never stops at the first failure; the summary lists every code and every failure. The Expert review page chooses the prefix per row (a row inherits the prefix of the row above until changed by hand); the Easy wizard uses one prefix for all, and offers Expert mode for mixed prefixes. The last prefix used is remembered on the project (`default_prefix_id`) and becomes the default next time.
10. **Expert inline editing** posts one field at a time as JSON to `POST /projects/{id}`; `Projects::update` is partial (only keys present are changed, keys the type does not use are ignored) and audits only real changes. The Easy "Edit details" page posts the whole form to the same route.
11. **Attachments** are stored under `FILES_PATH/projects/{id}/` with a random name; the original name, mime and size are in the row. Executable/script extensions are refused; size limit from setting `max_upload_mb`. Delete is a soft delete (`deleted_at`). Images and PDFs can be shown inline (`?inline=1`); everything else downloads with `X-Content-Type-Options: nosniff`.
12. **Tasks**: anyone who can open the project may tick off a task they own (the home page uses `POST /projects/{id}/tasks/{tid}/done`); adding, removing and ticking other people's tasks needs `projects.edit`.
13. **Reordering** works without JavaScript (up/down forms) and with drag-and-drop (posts the whole order). Sequences are re-packed 1..n after removes and moves.
14. **Search** parses the query with `CodeFormat`: a bare number matches the project number, `E…` matches E numbers by prefix range (like the lookup API), prefix+number matches `sell_number_normalized` by prefix, and the words run through FULLTEXT on `chroma_projects(title, description)` and on `chroma_project_items(description)` (new idempotent index in `db/migrations/0030_project_items_fulltext.sql`).
15. **`projects.js` is loaded without `defer`** from the views' `head` section: the vendored Alpine build starts in a microtask right after its own script runs, and the layout prints the `head` section after Alpine's tag, so a deferred module script would register its components too late.
16. **Exports** of the projects list require `codes.export` (the "Export lists" permission in the catalogue) in addition to `projects.view`.

### Review fixes (round 2)

17. **Closed projects refuse writes in the domain.** `Projects::assertOpen()` is called by `Projects::update()` and by every item write (`add`, `update`/`setStatus`, `reorder`, `move` (both projects), `remove`, `linkExisting`, `assignInternal`, `assignSell`, `batchAssign`). The message is "Project 106 is completed, so you cannot …. Reopen it from its page first." Both modes share it; the Easy wizards also check at their start step so nobody walks through the steps for nothing. `complete()/cancel()/reopen()` and tasks/notes/attachments are not blocked (tasks are closed from the home page after completion; notes on a completed project are a record, not a change).
18. **An item that already holds a code keeps it.** `Items::normalizeOne()` refuses `existing_ref` / `internal_code_id` / `sell_number_id` that would replace a different E# or sell number on an item ("already has E9179. To change it, void or unlink that E number from its code page first."). Picking the code it already holds is a no-op. Linking a code to an item that had none is audited as `item.link_code` with before/after ids.
19. **The lookup component's `customer_id_text` is accepted everywhere** (`Projects::resolveCustomer()` reads `customer_text` first, then `customer_id_text`; the controllers also map it), so the Expert page and the wizard behave the same for a typed-in new customer.
20. **Team can be cleared.** The Easy edit page posts `team_present=1`; the controller then always passes `team` (possibly empty) to `update()`, which removes everybody and writes the `team_changed` activity entry.
21. **Alpine components are composed with property descriptors, not `Object.assign`**, so getters such as `full` (items grid cap) and `allOn` (select-all) stay live. `itemsGrid` now owns `type`/`meta` on the Expert new-project page; `itemsSection` = `batchSelect` + `itemsOrder` on the project page.
22. **Easy list on a phone is a card stack** (CSS only, `data-label` per cell, under 640px); Expert keeps the dense table with sideways scroll by design. Easy item rows always show "Proofs: Y (n)" or "Proofs: N".
23. **Export has no silent cap**: the controller pages through `list()` in chunks of 1000 until every matching project is in the file.


## Decisions: Reports page and read-only API (module G)

- **Reports are pure reads.** `Domain\Reports\Reports` returns one shape for every report (`tables` keyed by name, each with `columns` + `rows`, plus report-specific extras) so the controller renders and exports the same data. The only write is an audit entry on export (`report.export`).
- **Exporting a report requires `codes.export` as well as `reports.view`**, matching the permission catalogue ("Download code logs, lookups and reports as CSV or Excel"). The CSV/Excel buttons are hidden without it; the route enforces it.
- **Confidential projects are excluded from every report** unless the viewer holds `projects.view_confidential` **or is that project's lead (`assigned_user_id`), creator or team member** — the same rule as the project pages (`Domain\Projects\Visibility`), so a tech's reports home never disagrees with their projects list. Headline cards follow the same rule. The viewer id is an int and is inlined in the SQL fragment because the callers mix named and positional parameters. (Changed after review: the first build hid confidential projects from their own lead.)
- **"Today" for aging is the date in the app timezone** (`today()`), passed into the domain class so the maths is testable with a pinned date. Age = `DATEDIFF(today, date_submitted)`; a project with no submitted date falls back to its creation date; a submitted date in the future counts as 0-7 days. The date is inlined as a validated SQL literal because it appears several times in one statement and PDO native prepares reject a reused named placeholder.
- **Turnaround** uses `DATEDIFF(date_completed, date_submitted)` on completed projects with both dates; the date-range filter is on the completed date. Median is computed in PHP (MariaDB has no MEDIAN). Default window: the last 12 months.
- **Codes per month** counts by `date_assigned` (a DATE column) with `DATE_FORMAT(..., '%Y-%m')`; the 12 months end with the month of the chosen "last month" (default: current month). Voided codes are still counted as assigned (the number was consumed) and reported separately in a "voided" column. Retired prefixes with zero codes in the window are hidden; active prefixes always show, so a quiet prefix is visible.
- **Proofs** are dated by `COALESCE(item.date_completed, item.date_started, project.date_submitted, DATE(item.created_at))` and attributed to `COALESCE(item.assigned_user_id, project.assigned_user_id)`, because the schema stores no "proof made on" date. Documented in the help page.
- **Items done vs total**: an item counts as done when its status has `is_done = 1`; items with no status count as not done. Default scope is open projects; "Completed"/"All" are available.
- **Bad filter input never blocks the page.** `Reports::parseFilters` drops an unreadable date or swaps a reversed range and returns a plain-language note shown in a warning callout, instead of throwing (a ValidationException on a GET would redirect in a loop).
- **Visuals are CSS/inline bars only** (no chart library): one hue per chart, thin bars with the exact number always in an adjacent cell, `aria-hidden` on the decorative bar; the monthly column chart carries `role="img"` with a label pointing to the table. Aging buckets use amber/red for 31-60 and 60+ so urgency is readable, with the bucket label and count always printed.
- **API auth happens in the controller**, not the router: routes are `->public()->noCsrf()`, and every failure is JSON regardless of the client's `Accept` header (App's error path would otherwise render HTML for a client that forgot the header). There is deliberately **no `?token=` query-string fallback**: a token in the URL ends up in nginx access logs, browser history and Referer headers (removed after review). Any other path under `/api/v1`, and any write method on an endpoint, is caught by a last-registered `/api/v1{any:.*}` route that answers JSON 404 / 405 (`Allow: GET, HEAD`) instead of the framework's HTML error page, because `App::errorResponse` is not mine to change.
- **API envelope**: lists `{data, page, per_page, total}`; single objects `{data}`; errors `{error}`. `per_page` is clamped to 1..200. `updated_since` accepts any ISO 8601 date/date-time and is compared to `chroma_projects.updated_at` in UTC.
- **`/api/v1/codes/internal/{code}` without a version** returns the base (versionless) row when it exists, otherwise the first version on file, and always lists `versions` so the caller can ask for a specific one. A version that does not exist is a 404.
- **Code search order**: an E-number-shaped query (`E6374`, `6374-10`, bare digits) is treated as an E number first; then, **only when the letters are a configured prefix** (`chroma_code_prefixes.code`), a sell-number spelling (prefix match on `sell_number_normalized`); otherwise free text via boolean-mode FULLTEXT on the description. Without the prefix check, "pantone 300" / "stress test 4" parsed as PANTONE300 / STRESSTEST4 and found nothing (review finding). A one-word query like `Pantone300` is split into `Pantone 300` before the fulltext search. The old `description LIKE 'q%'` half was dropped: it was an unindexed scan and unescaped `%`/`_` listed the whole table; `%` and `_` are now plain text.
- **Projects in the API come from `v_chroma_project_status`** (joined to `chroma_projects` for `updated_at` and `customer_id`), so the view and the API can never disagree about confidentiality.
- **Screenshot fixtures**: projects numbered 9901-9916 titled "[rpt-fixture] …", three "[rpt-fixture]" customers, a user `rptfixture` and an API token "[rpt-fixture] curl" were created in the dev DB for screenshots and removed again at the end of the build.

- **Empty states say what actually happened** (after review): a page number past the end of the aging list says so and links to page 1 instead of "Nothing in this bucket"; the R&D and Items empty states offer "show all statuses" only when a narrower status is selected, "Clear filters" when other filters are set, and a link to Projects when there is simply nothing yet.
- **Phone width**: side-by-side report sections get `min-width: 0` so a wide table scrolls inside `.table-wrap` instead of widening the page, and the hidden radio inside a filter chip is pinned to 1px inside the chip (the base `.filters input { min-width: 140px }` rule out-specified `.sr-only`, which pushed the page to 416-545px wide).
